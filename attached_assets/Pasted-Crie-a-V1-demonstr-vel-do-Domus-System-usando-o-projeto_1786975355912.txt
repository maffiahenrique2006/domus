Crie a V1 demonstrável do Domus System usando o projeto atual.

Antes de implementar:

1. Leia integralmente o DESIGN.md e os arquivos do design system que já existem no projeto.

CONTEXTO DO PRODUTO

O Domus System é um sistema que cria sistemas de gestão personalizados para cada empresa.

Esta aplicação deve demonstrar como o Domus foi configurado para uma empresa fictícia específica. Não estamos construindo agora o construtor interno da Domus nem uma inteligência artificial funcional.

A interface deve parecer um sistema real, coerente e utilizável, mas todos os dados serão fictícios e locais. Não haverá banco de dados real, autenticação real, integrações externas, pagamentos ou automações reais nesta versão.

EMPRESA FICTÍCIA

Nome: Vértice Espaços

Descrição:
A Vértice Espaços é uma empresa fictícia de arquitetura comercial que projeta e executa lojas, escritórios, restaurantes e espaços temporários para marcas.

Modelo de operação:

- Recebe pedidos de clientes e solicitações internas.
- Analisa e transforma demandas aprovadas em projetos.
- Organiza cada projeto por fases, responsáveis, prazos e orçamento.
- Controla receitas, despesas, pagamentos e margem por projeto.
- A direção precisa enxergar rapidamente o que exige atenção.

OBJETIVO DA V1

Criar uma aplicação web responsiva, navegável e visualmente refinada que permita demonstrar:

- a visão geral da empresa;
- o recebimento e acompanhamento de demandas;
- a gestão dos projetos;
- o controle financeiro;
- a conexão entre demanda, projeto e resultado financeiro;
- a capacidade da Domus de adaptar o sistema à operação de uma empresa.

RELAÇÃO ENTRE OS MÓDULOS

A aplicação não deve parecer quatro páginas isoladas.

Implemente conexões navegáveis:

- uma demanda aprovada pode originar um projeto;
- o projeto mantém referência à demanda de origem;
- lançamentos financeiros podem estar ligados a um projeto e cliente;
- alertas da visão geral levam ao registro correspondente;
- alterações locais devem atualizar os indicadores relacionados quando for viável.

COMPORTAMENTOS DA DEMONSTRAÇÃO

As interações precisam funcionar no navegador:

- navegação entre páginas;
- filtros;
- busca;
- abertura e fechamento de detalhes;
- criação e edição por formulários;
- alteração de status;
- conversão demonstrativa de demanda em projeto;
- atualização local de indicadores;
- feedback de sucesso;
- estados vazios;
- validação básica dos formulários;
- persistência com localStorage, se for adequada à arquitetura atual.

Não criar botões sem ação. Quando uma funcionalidade real estiver fora do escopo, não exibir um botão que simule uma promessa inexistente.

DADOS E TECNOLOGIA

- Todos os nomes, empresas, projetos e valores são fictícios.
- Use dados mockados centralizados e bem estruturados.
- Não use serviços externos.
- Não solicite chaves de API.
- Não implemente autenticação real.
- Não implemente IA ou chatbot funcional.
- Não conecte banco de dados nesta versão.
- Mantenha a estrutura preparada para uma futura troca dos dados locais por uma API.
- Use a stack e os padrões já presentes no projeto.
- Não substitua dependências existentes sem necessidade.
- Use ícones da biblioteca já instalada; não use emojis como ícones da interface.

DIREÇÃO DE EXPERIÊNCIA

A sensação deve ser de uma central de gestão personalizada, clara e confiável.

Prioridades:

- visão antes do detalhe;
- informação importante fácil de encontrar;
- hierarquia visual forte;
- textos em português;
- valores em reais;
- datas no padrão brasileiro;
- interface profissional e sóbria;
- boa legibilidade;
- acessibilidade;
- responsividade;
- densidade equilibrada;
- acabamento visual de produto real.

Evite:

- aparência de template genérico de dashboard;
- excesso de gráficos decorativos;
- grandes blocos de cor sem função;
- textos vagos;
- lorem ipsum;
- dados desconectados;
- componentes que não seguem o DESIGN.md;
- modificar o design system para acomodar decisões improvisadas.
